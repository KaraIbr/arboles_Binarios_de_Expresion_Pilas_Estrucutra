Ahora veamos la lógica pieza por pieza. La organicé con una idea sencilla: cada archivo tiene una sola tarea, recibe algo y entrega algo, como en una cadena de producción. El Lexer recibe el texto y entrega la lista de piezas. No sabe nada de árboles. El Parser recibe esa lista y entrega la raíz del árbol; sabe cómo se acomodan las piezas, pero no cómo se calcula. Para crear cada nodo usa la clase TreeNode, del archivo Node, que lo único que hace es guardar INFO, IZQ y DER. Los recorridos reciben la raíz y entregan una lista de nodos en preorden, inorden o posorden. No les importa si un nodo es un número o un operador: solo lo visitan. La pila es la más independiente de todas. Guarda valores, los saca y consulta el de arriba, y no tiene idea de que está guardando números de una operación; podría guardar cualquier otra cosa. El evaluador es el que reúne a las demás: recibe el árbol, le pide el posorden, usa una pila y entrega la lista de pasos junto con el resultado. Y el archivo notations calcula el valor de cada recorrido, lo que vimos hace un momento. Por cierto, ese archivo reutiliza la misma pila y la misma función que hace las operaciones; no tuve que escribirlas otra vez. ¿Qué gano con esta separación? Que cada pieza se puede revisar sola. Si un resultado saliera mal, puedo comprobar primero si las piezas son correctas, después si el árbol es correcto, y así encontrar el error rápido. Las pruebas automáticas hacen exactamente eso. Y si lo hubiera hecho al revés, por ejemplo, si el Parser leyera directamente el texto carácter por carácter, tendría que hacer él mismo el trabajo del Lexer. Tendría dos tareas mezcladas, el código sería más largo y cualquier error sería más difícil de encontrar.
